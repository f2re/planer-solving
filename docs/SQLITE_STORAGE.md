# SQLite-хранилище и миграция данных

## Назначение

Начиная с версии 2.5 рабочие пространства, преподаватели и шаблоны хранятся в `data/planner-solving.sqlite3`. Переход устраняет потерю изменений при параллельной работе и позволяет использовать транзакции, ограничения целостности и проверяемые миграции.

## Первый запуск после обновления

Последовательность штатного запуска:

1. `tools.migrate` проверяет и при необходимости обновляет прежний `workspaces.json`.
2. `tools.healthcheck` импортирует приложение.
3. `ApplicationContext` проверяет версию существующей SQLite-базы.
4. Если базы ещё нет, `SQLiteWorkspaceStore` создаёт схему и импортирует `workspaces.json`.
5. Если `workspaces.json` отсутствует, создаётся основное пространство из `teachers.json`.
6. После импорта создаются атомарные совместимые JSON-зеркала.
7. Выполняется `PRAGMA quick_check`.
8. Только после успешной проверки запускается Uvicorn.

Оператору не требуется вручную запускать конвертацию.

## Файлы

```text
data/
  planner-solving.sqlite3      основной файл базы
  planner-solving.sqlite3-wal  журнал WAL во время работы
  planner-solving.sqlite3-shm  служебная память WAL
  workspaces.json              совместимое атомарное зеркало
teachers.json                  зеркало преподавателей основного пространства
```

Файлы SQLite и их WAL-компоненты не включаются в Git. В офлайн-установке весь каталог `shared/data` входит в резервную копию.

## Транзакции

Каждая операция изменения выполняется в отдельной короткой транзакции:

```sql
BEGIN IMMEDIATE;
-- изменение пространства, преподавателя или шаблона
-- обновление времени изменения
COMMIT;
```

`BEGIN IMMEDIATE` резервирует запись до вычисления следующего идентификатора и тем самым предотвращает потерю обновлений при параллельных запросах.

JSON-зеркала формируются из того же состояния, пока транзакция удерживает блокировку записи. Если запись зеркала не удалась, транзакция SQLite откатывается и API возвращает ошибку.

## Ограничения целостности

База гарантирует:

- уникальное название пространства без учёта регистра;
- уникальное нормализованное ФИО внутри пространства;
- уникальное название шаблона внутри пространства;
- каскадное удаление преподавателей и шаблонов при удалении пространства;
- существование не менее одного пространства на уровне прикладной транзакции;
- корректный формат и порядок дат семестра;
- отказ от открытия базы более новой версии.

## Проверка

```bash
python -m tools.healthcheck --app-root . --data-dir data
```

Проверяются:

- импорт фабрики приложения;
- наличие SQLite-файла и JSON-зеркала;
- `PRAGMA quick_check`;
- версия схемы SQLite;
- количество пространств;
- наличие основного пространства;
- версия совместимого JSON-документа.

Ручная диагностическая проверка:

```bash
sqlite3 data/planner-solving.sqlite3 'PRAGMA quick_check; PRAGMA user_version;'
```

Для штатной эксплуатации установка `sqlite3` не требуется: Python содержит встроенный драйвер.

## Резервное копирование

Перед офлайн-обновлением служба останавливается, после чего архивируется весь `shared/data`. Это важно для согласованного копирования основной базы и WAL.

Не следует копировать только `planner-solving.sqlite3` из работающего процесса, игнорируя `-wal`. Для ручной онлайн-копии используйте SQLite backup API или предварительно остановите службу.

## Откат

Штатный `rollback.sh`:

1. останавливает службу;
2. возвращает предыдущий выпуск;
3. восстанавливает архив `shared/data`, `teachers.json` и `config.json`;
4. запускает предыдущую службу;
5. проверяет `/api/health`.

JSON-зеркало позволяет предыдущему выпуску прочитать данные, но штатный откат всё равно восстанавливает согласованную резервную копию, соответствующую версии кода.

## Повреждение или неподдерживаемая версия

Приложение не пытается «починить» или понизить неизвестную SQLite-схему. Запуск прекращается до записи данных.

При сообщении о повреждении:

1. остановить службу;
2. сохранить копии `planner-solving.sqlite3`, `-wal`, `-shm` и JSON-зеркала;
3. выполнить `PRAGMA integrity_check`;
4. восстановить последний штатный архив либо импортировать проверенное JSON-зеркало в чистую базу;
5. повторить `tools.healthcheck`.

## Многопроцессный режим

SQLite устраняет конфликты нескольких запросов и нескольких процессов одного приложения. Для текущей нагрузки рекомендуется один Uvicorn worker: операции разбора Excel ресурсоёмки, а фоновые задачи пока не вынесены в отдельную очередь.

При переходе к нескольким узлам необходимо вынести базу в сетевую СУБД и добавить распределённое хранилище файлов. Размещать SQLite на NFS/SMB не рекомендуется.
