# Система миграций данных

## Назначение

Код приложения и рабочие данные версионируются отдельно. Версия приложения хранится в `VERSION`, версия структуры `data/workspaces.json` — в корневом поле `version`.

Текущая версия схемы задаётся константой `CURRENT_SCHEMA_VERSION` в `src/data_migrations.py`.

## Правила

1. Миграции выполняются только вперёд и строго по одной версии.
2. Перед изменением создаётся побайтовая резервная копия исходного файла.
3. Запись выполняется атомарно через временный файл и `os.replace`.
4. Повторный запуск одной миграции безопасен: файл актуальной версии не изменяется.
5. Приложение отказывается работать с данными более новой версии.
6. Откат приложения через офлайн-установщик всегда сопровождается восстановлением соответствующей резервной копии данных.

## Поддерживаемая исходная миграция

### 0 → 1

Поддерживаются три прежних состояния:

- файл `workspaces.json` отсутствует;
- в файле находится старый список преподавателей;
- объект пространств существует, но не имеет поля `version`.

Список преподавателей преобразуется в `Основное пространство`. Если отдельный файл данных отсутствует, используется совместимый `teachers.json`.

## Проверка без записи

```bash
python -m tools.migrate \
  --data-dir data \
  --legacy-teachers teachers.json \
  --backup-dir data/backups/migrations \
  --check
```

Машиночитаемый отчёт:

```bash
python -m tools.migrate --check --json
```

## Применение

```bash
python -m tools.migrate \
  --data-dir data \
  --legacy-teachers teachers.json \
  --backup-dir data/backups/migrations
```

Штатный `start_web.sh` и офлайн-установщик выполняют эту команду автоматически.

## Добавление новой миграции

Для перехода, например, с версии 1 на 2:

1. увеличить `CURRENT_SCHEMA_VERSION` до `2`;
2. добавить функцию `migrate_1_to_2(payload, legacy_teachers)`;
3. функция должна возвращать новый объект с `version: 2`;
4. зарегистрировать функцию в `MIGRATIONS[1]`;
5. не изменять исходный объект на месте — использовать копию;
6. дополнить `validate_document` новыми обязательными условиями;
7. добавить тесты прямого перехода, повторного запуска и отказа на повреждённых данных;
8. проверить обновление через полный офлайн-сценарий.

Пример:

```python
def migrate_1_to_2(payload, legacy_teachers=None):
    migrated = deepcopy(payload)
    for workspace in migrated["workspaces"]:
        workspace.setdefault("new_field", "default")
    migrated["version"] = 2
    return migrated

MIGRATIONS = {
    0: migrate_0_to_1,
    1: migrate_1_to_2,
}
```

## Совместимость отката

Обратные миграции намеренно не выполняются. Они значительно повышают риск потери данных. Для отката используется архив `shared/backups/before-<версия>-<дата>.tar.gz`, содержащий состояние данных до обновления.

Если новая версия уже использовалась и пользователи внесли изменения, перед откатом создаётся аварийная копия текущего состояния.
