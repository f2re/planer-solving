# Система миграций данных

## Два уровня версии

Код приложения и постоянные данные версионируются независимо:

- `VERSION` — версия выпуска приложения;
- `CURRENT_SCHEMA_VERSION` — версия совместимого JSON-документа;
- `SQLITE_SCHEMA_VERSION` — версия основной SQLite-схемы (`PRAGMA user_version`).

JSON нужен для первичного перехода со старых выпусков и совместимого отката. После версии 2.5 источником истины является SQLite.

## Порядок обновления

1. Служба останавливается.
2. Каталог общих данных архивируется целиком.
3. `tools.migrate` последовательно обновляет прежний `workspaces.json`.
4. Новый выпуск импортирует приложение через `tools.healthcheck`.
5. `ApplicationContext` проверяет существующую SQLite-схему.
6. При первом запуске SQLite создаётся из проверенного JSON.
7. Выполняется `PRAGMA quick_check`.
8. Только после успешных проверок переключается и запускается служба.

## Правила JSON-миграций

1. Миграции выполняются только вперёд и по одной версии.
2. Исходный объект не изменяется на месте.
3. Перед записью создаётся резервная копия.
4. Запись выполняется атомарно через временный файл и `os.replace`.
5. Повторный запуск актуальной миграции не изменяет файл.
6. Документ более новой версии не переписывается.

### Поддерживаемый переход 0 → 1

Поддерживаются:

- отсутствие `workspaces.json`;
- прежний список преподавателей в корне JSON;
- объект пространств без поля `version`.

Список преподавателей преобразуется в основное пространство. Если отдельный документ отсутствует, используется `teachers.json`. Новое пространство получает актуальный диапазон ближайшего учебного семестра, а не фиксированные даты определённого года.

Проверка без записи:

```bash
python -m tools.migrate \
  --data-dir data \
  --legacy-teachers teachers.json \
  --backup-dir data/backups/migrations \
  --check
```

Применение:

```bash
python -m tools.migrate \
  --data-dir data \
  --legacy-teachers teachers.json \
  --backup-dir data/backups/migrations
```

## Правила SQLite-миграций

Текущая схема задаётся `SQLITE_SCHEMA_VERSION` в `src/sqlite_workspace_store.py`.

При добавлении версии `N → N+1` необходимо:

1. увеличить `SQLITE_SCHEMA_VERSION`;
2. выполнить миграцию внутри одной транзакции;
3. обновить `PRAGMA user_version` только после успешных SQL-операций;
4. сохранить совместимое JSON-зеркало нового состояния;
5. не открывать базу, если её версия выше поддерживаемой;
6. добавить тесты прямого перехода, повторного запуска, повреждённой базы и параллельной записи;
7. проверить офлайн-обновление и откат на реальном архиве.

Автоматическое понижение схемы запрещено. Обратный переход выполняется восстановлением согласованной резервной копии, созданной до обновления.

## Проверка после миграции

```bash
python -m tools.healthcheck --app-root . --data-dir data
```

Проверяются версии обоих форматов, целостность JSON-зеркала, `PRAGMA quick_check`, наличие таблиц, основного пространства и импорт фабрики приложения.

## Совместимость отката

Штатный офлайн-установщик архивирует весь `shared/data`, включая SQLite и WAL, а также `teachers.json` и `config.json`. Откат восстанавливает код и данные одной согласованной точкой.

Если после обновления пользователи уже внесли изменения, установщик сначала сохраняет аварийную копию текущего состояния. JSON-зеркало облегчает ручное восстановление, но не заменяет штатный архив.

Подробности: [`SQLITE_STORAGE.md`](SQLITE_STORAGE.md) и [`OFFLINE_UPDATE.md`](OFFLINE_UPDATE.md).
