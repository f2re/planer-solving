# Аудит критических неисправностей и восстановления — 2.19

## Цель

Критическая неисправность не должна оставлять оператора с сообщением «что-то пошло не так». Для каждого отказа система должна сообщить:

1. что именно не выполнено;
2. сохранена ли текущая работа;
3. можно ли безопасно повторить действие;
4. что сделать оператору;
5. какой штатный инструмент использовать администратору;
6. код инцидента для сопоставления с журналом.

Предметные расхождения расписания по-прежнему не считаются критическими: они разрешаются автоматически или корректируются в редакторе.

## Реализованный контракт API

Все `ApplicationError`, ошибки рабочих пространств и неперехваченные исключения возвращают:

```json
{
  "detail": "понятное описание",
  "code": "стабильный_код",
  "incident_id": "короткий идентификатор",
  "recovery": {
    "title": "название неисправности",
    "severity": "critical",
    "retryable": true,
    "state_preserved": true,
    "guidance": "последовательность действий",
    "actions": []
  }
}
```

Тот же идентификатор возвращается заголовком `X-Planner-Incident` и записывается в серверный журнал.

## Матрица отказов

| Сценарий | Что сохраняется | Решение оператора | Инструмент администратора |
|---|---|---|---|
| Сеанс истёк | Завершённые запуски в истории | Открыть историю или начать новый сеанс | Не требуется |
| Manifest сеанса повреждён | Исходные файлы могут оставаться в каталоге сеанса | Не удалять сеанс, открыть диагностику | `planner-solving-doctor` |
| Исходный/готовый файл отсутствует | Остальные файлы, разметка и история | Заменить только файл, повторить из истории | Проверка каталога `shared` и `output` |
| Черновик изменён в другой вкладке | Обе версии, серверная не перезаписана | Восстановить серверную ревизию | Не требуется |
| Черновик слишком велик | Последняя серверная ревизия | Сформировать промежуточный результат или убрать лишние файлы | Не требуется |
| Добавление/замена/удаление не закоммичены | Прежний состав сеанса восстановлен | Проверить хранилище и повторить одну операцию | Диагностика диска и прав |
| SQLite недоступна/повреждена | Активные файлы сеанса не удаляются | Не изменять данные, открыть диагностику | Резервная копия, `quick_check`, `--repair` |
| Нет места или прав на `output` | Исходники, разметка, ручные решения и черновик | Освободить место/исправить права и снова сформировать | `planner-solving-doctor`, `df`, `namei` |
| Недельный шаблон отсутствует | Общее расписание | Скачать общее; добавить шаблон и повторить недельный экспорт | Добавить `obrazec/Недельное.xlsx` |
| Ошибка оформления Excel | Все разобранные данные | Скачать плоский восстановленный XLSX | Не требуется |
| Внутренняя ошибка | Активный сеанс не удаляется | Повторить один раз, затем передать код инцидента | Журнал systemd + отчёт doctor |
| Python/venv/библиотеки повреждены | Каталог `shared` и предыдущий выпуск | Не ставить пакеты глобально | Установщик `--python bundled --strict-python --repair` |
| systemd/порт не запускается | Данные в `/opt/planner-solving/shared` | Не переустанавливать данные | `run-service.sh --check`, `systemctl`, `journalctl` |

## Интерфейс оператора

Критический ответ API открывает Центр восстановления. Он показывает:

- понятное название и описание;
- индикатор сохранности текущей работы;
- возможность повторения;
- код ошибки и код инцидента;
- кнопки, соответствующие конкретному отказу;
- встроенную диагностику каталогов, диска, SQLite и недельного шаблона;
- копируемые команды для администратора.

Поддерживаются действия:

- повторить исходный запрос;
- восстановить серверный черновик;
- открыть историю;
- начать новый сеанс;
- заменить только текущий файл;
- обновить рабочие пространства;
- перейти к данным пространства;
- повторить формирование;
- открыть список файлов;
- открыть диагностику;
- скопировать код инцидента или административную команду.

Ошибки запросов Axios и `fetch` обрабатываются одинаково. Локальный обработчик по-прежнему может показать краткое уведомление, но критическая неисправность всегда имеет отдельный путь решения.

## Диагностический endpoint

`GET /api/system/recovery` безопасно проверяет:

- запись в `data`, `input`, `output` и каталог временных сеансов;
- свободное место;
- открытие SQLite, `PRAGMA quick_check` и версию схемы;
- наличие шаблона недельного расписания;
- количество активных временных сеансов.

Endpoint не возвращает содержимое документов, пароли, stack trace или серверный журнал.

## Командные инструменты

```bash
sudo planner-solving-doctor --output /tmp/planner-solving-doctor.txt
sudo planner-solving-python
sudo systemctl status planner-solving --no-pager -l
sudo journalctl -u planner-solving -n 160 --no-pager
sudo ./install-planner-solving.sh --python bundled --strict-python --repair
```

`tools.service_preflight` и `tools.healthcheck` теперь выводят не только ошибку, но и конкретное решение. JSON-режим содержит `issues`, `recommendations` и `admin_commands`.

## Непреодолимые автоматически ситуации

Система не может сама:

- вернуть удалённый вне приложения файл без резервной копии;
- освободить чужой системный раздел без решения администратора;
- восстановить физически повреждённую SQLite без исправного снимка;
- исправить аппаратную ошибку диска;
- получить права, которые операционная система запретила пользователю службы.

В этих случаях приложение сохраняет доступное состояние, запрещает разрушительные автоматические действия и выдаёт конкретный инструмент диагностики и последовательность восстановления.

## Критерии приёмки

- у каждого критического кода есть guidance и хотя бы одно действие;
- внутренний отказ имеет код инцидента и не раскрывает stack trace;
- `ENOSPC`, `EACCES`, `EROFS` и ошибки записи результата распознаются отдельно;
- ошибка SQLite распознаётся как отказ хранилища;
- критические ошибки Axios и `fetch` открывают один Центр восстановления;
- диагностика доступна из окна отказа;
- оператор может повторить действие без потери активного сеанса;
- CLI объясняет, что исправить, и не рекомендует удалять `shared`;
- автономный пакет содержит все новые модули и проверки.
