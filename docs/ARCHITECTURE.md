# Архитектура Planner Solving

## Принципы

Версия 2.5 использует явную композицию приложения без динамического исполнения модулей, подмены методов классов и изменения уже зарегистрированных маршрутов.

Основные правила:

1. `web/backend/main.py` содержит только ASGI-точку входа.
2. `web/backend/app_factory.py` создаёт экземпляр FastAPI функцией `create_app()`.
3. Все изменяемые зависимости принадлежат конкретному `ApplicationContext`.
4. Каждый функциональный блок возвращает независимый `APIRouter`.
5. Статический интерфейс монтируется последним, после всех API-маршрутов.
6. Единственный рабочий репозиторий пространств — SQLite.
7. Ошибки предметной области не превращаются в необработанные HTTP 500.

## Сборка приложения

```text
web.backend.main
  └─ create_app()
      ├─ ApplicationContext
      │   ├─ ApplicationPaths
      │   ├─ AnalysisSessionStore
      │   └─ SQLiteWorkspaceStore
      ├─ analysis router
      ├─ session/download router
      ├─ workspace router
      ├─ schedule router
      ├─ system router
      └─ StaticFiles /
```

`create_app(base_dir=..., workspace_repository=...)` допускает подстановку временного каталога или тестового репозитория. Тесты больше не изменяют глобальные переменные уже созданного приложения.

## Модули backend

- `app_factory.py` — композиция FastAPI и порядок маршрутов;
- `app_context.py` — пути, зависимости и жизненный цикл сеансов;
- `analysis_api.py` — потоковая загрузка, первичный анализ и подбор шаблонов;
- `session_api.py` — предпросмотр, удаление сеанса и скачивание результата;
- `workspace_api.py` — пространства, преподаватели, шаблоны, импорт и экспорт;
- `workspace_schedule.py` — контрольный разбор и формирование расписаний;
- `system_api.py` — health-check и сведения о версиях;
- `errors.py` — единый перевод прикладных исключений в безопасные ответы API.

Запрещено:

- выполнять другой модуль через `exec`;
- подменять методы классов при импорте;
- удалять или переставлять `app.router.routes` после регистрации;
- обращаться из роутера к изменяемым глобальным путям;
- возвращать пользователю traceback или текст произвольного внутреннего исключения.

Эти ограничения проверяются CI.

## Сеансы анализа

`AnalysisSessionStore` отвечает за:

- создание UUID-сеанса;
- безопасное разрешение путей;
- атомарную запись `manifest.json`;
- хранение загруженных книг и снимков списка преподавателей;
- удаление истёкших сеансов;
- защиту от выхода за пределы каталога сеанса.

Файлы расписаний не являются постоянными рабочими данными. Они удаляются оператором либо автоматически после истечения срока хранения.

## Хранилище пространств

Источник истины — `data/planner-solving.sqlite3`.

Таблицы:

- `metadata` — основное пространство и служебные версии;
- `workspaces` — параметры пространства и даты семестра;
- `teachers` — преподаватели с уникальностью внутри пространства;
- `templates` — шаблоны разметки с JSON-полем координат.

SQLite работает с:

- `foreign_keys=ON`;
- режимом WAL;
- `busy_timeout=30000`;
- короткими транзакциями `BEGIN IMMEDIATE` для изменений;
- уникальными индексами по названиям и нормализованным ФИО.

Подробности: [`SQLITE_STORAGE.md`](SQLITE_STORAGE.md).

## Совместимость и откат

`data/workspaces.json` и `teachers.json` больше не являются источником истины. Они обновляются атомарно после каждой успешной операции как совместимые зеркала.

Это позволяет:

- использовать существующие CLI-сценарии чтения преподавателей;
- экспортировать состояние без специальных SQLite-инструментов;
- откатить приложение штатным офлайн-установщиком вместе с резервной копией данных.

Новый код не должен читать рабочее состояние непосредственно из этих JSON-файлов.

## Добавление нового API

1. Создать функцию `build_<domain>_router(context) -> APIRouter`.
2. Передавать зависимости через `ApplicationContext` или отдельный протокол.
3. Использовать предметные исключения для ожидаемых ошибок.
4. Зарегистрировать роутер в `create_app()` до `StaticFiles`.
5. Добавить HTTP-тест через `create_app(tmp_path)`.
6. Проверить OpenAPI и отсутствие дублирующихся маршрутов.

## Добавление постоянных данных

1. Увеличить `SQLITE_SCHEMA_VERSION`.
2. Добавить последовательную миграцию SQLite.
3. Не изменять и не понижать базу с более новой версией.
4. Обновить JSON-зеркало, если данные нужны для совместимого отката.
5. Добавить тесты прямой миграции, повторного запуска, параллельной записи и повреждённой базы.
6. Проверить офлайн-обновление и автоматический откат.
